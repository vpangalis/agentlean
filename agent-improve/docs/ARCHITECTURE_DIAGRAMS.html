D02

DMAIC Phase Subgraph — Internal Node Structure

Five nodes inside every phase subgraph. The planner fires on every coaching cycle, not just once. Two cycles: planner ↔ executor (field-by-field coaching), executor ↔ validation (revision loop). Belt interrupt fires at gate_review, not at validation. Checkpoint commits only at gate_apply. Refs: §17, §18, §20, §23, §48, §68.

Two cycles, not a pipeline: Cycle 1 (Planner ↔ Executor) runs field by field — the planner fires after every executor step to decide whether to continue, move to the next field, or trigger the gate. D04

Only ONE box in the entire system is a true agent (LLM + bound tools + decision loop). Everything else is a router, a function, an interrupt point, or a role label. This matters because "agent" implies tool-selection capability — only the phase_executor has that. Refs: Terminology reference section, §5, §11, §23.

Supervisor State and Gate Flags — Routing Mechanism

How the supervisor decides which phase to run. SupervisorState holds five boolean flags. Supervisor reads top to bottom, routes to first False. Gate apply writes a flag to True on Belt approval. The re-approval cascade shows what happens when a Belt baseline change invalidates prior phases. Refs: §17, §52, gate_apply_node logic.

The Re-Approval Cascade

Belt changes a baseline during the Analyse gate review. The policy advisory detects that this change invalidates prior phases. It flips earlier flags back to False.

Before D: True M: True A: False
↓ policy advisory runs inside gate_apply
After D: False M: False A: False
Policy advisory flips Define and Measure back to False.
Supervisor reads top to bottom — first False is now Define, not Analyse.
Supervisor routes to Define subgraph, not Analyse.
The Belt must re-approve earlier phases before Analyse can proceed.

Key rule: policy advisory runs inside gate_apply_node. It is non-blocking advice, not a separate node.
State scope rules SupervisorState is the ONLY state the parent graph can see.
Phase internal state (PhaseState, coaching turns, tool results) never propagates to the parent.
Cross-phase artifacts flow through AzureBlobStore, not through state.
gate_attempts lives in the checkpoint saver, never in route scope.
D08

Single-hop vs Multi-hop Retrieval — Inside the Executor

The CoachingPlan (from the phase planner) sets hop_type. Single-hop is the default for all phases except Analyse. Multi-hop is bounded at 3 by the Pydantic schema — not infinite. Each hop targets a different index; synthesis is a separate LLM call before response generation. Refs: §37, §40, §41, §71-D, DECISIONS.md §F7.

Single-hop — all phases except Analyse
P
Phase Planner sets hop_type = single CoachingPlan → focus_field + one tool from the tool_sequence.
1
Executor calls one retrieval tool rag_lookup_methodology, or rag_lookup_evidence, or rag_lookup_case_history. AzureAISearchRetriever filter set at constructor time — no invoke-time filter.
2
Result returned to executor One retrieval result in context. No synthesis step needed.
3
LLM call 1 — generate CoachingResponse From retrieval result + conversation + phase state.
Total LLM calls for retrieval: 1 (generation only).
If the Belt needs more detail, the ReAct loop can call more tools reactively — the planner is not involved at that point.
Multi-hop — Analyse phase only · bounded at 3 hops
P
Phase Planner sets hop_type = multi CoachingPlan → tool_sequence of exactly 3 tools. Bounded by Pydantic schema — not configurable at runtime.
1
Hop 1 — rag_lookup_methodology improve_knowledge_index · LSS Black Belt eBook · what the methodology says. filter: phase_relevance eq 'analyse' or 'general'
2
Hop 2 — rag_lookup_evidence improve_evidence_index · Belt-uploaded documents · real-world data for this case. filter: case_id (per-call constructor required)
3
Hop 3 — rag_lookup_case_history improve_case_index · completed case records · yokoten — how similar cases resolved. filter: status='completed' order: created_at desc
S
Synthesis LLM call — hop_results → synthesis_output Separate LLM call inside executor. Triangulates all three retrieval results before response generation. Root cause analysis structurally requires all three sources.
4
LLM call 1 — generate CoachingResponse From synthesis_output + conversation + phase state.
Total LLM calls for retrieval: 2 (synthesis + generation).
Open assumption — §F7: Planned multi-hop is only in analyse_executor_node. Other phases use standard ReAct. Whether ReAct is sufficient for non-Analyse phases with complex questions is unverified. To be validated during eval dataset phase (§75).
Why 3 hops for Analyse: Root cause triangulation requires all three sources independently — methodology (what should happen), evidence (what actually happened), case history (how similar problems resolved). The 3-hop structure is not arbitrary; it maps to these three distinct epistemological sources. Bounded at 3 by the CoachingPlan Pydantic schema to prevent runaway retrieval.
D09

Constraint Validation (L2c) & Retry with Accumulated Feedback

The four validation layers run cheapest-first inside validation_gate_node. Each failure appends to PhaseState.validator_feedback. The executor re-runs with the full accumulated list — not just the last error. A shared cap of 3 attempts (not 3 per layer) bounds the loop. Refs: §48, §68, D05, D06.

The Four Validation Layers — cheapest first, each fires only if previous passes
L2a — Coherence LLM
Every turn. Checks: is the response internally consistent? Does it contradict earlier confirmed fields? Uses operational_model (cheap). Fires on every executor output before L2b.
✗
On fail: Appends to validator_feedback. Increments gate_attempts. Executor re-runs with full feedback list. L2b, L2c, L2d do not fire this round.
L2b — Field Presence DETERMINISTIC
Gate boundary only. Checks required fields are populated in PhaseOutput. Plain Python — no LLM call. Binary: field present or not. Fires only if L2a passed.
✗
On fail: Appends missing field list to validator_feedback. L2c and L2d do not fire.
L2c — Constraint Validation LLM
Fires only if L2a + L2b passed. Uses operational_model.with_structured_output(ConstraintCheckResult). Checks the phase's constraint dict — a different set per phase. Returns per-constraint verdicts, not a single pass/fail.
Per-phase constraint dictionaries:
DEFINE baseline, target, scope, timeline
ANALYSE root_cause, validation
+ risk (value-dependent: fires when risk_level == "low")
IMPROVE budget, deadline, measurement
CONTROL monitoring, sustainability, handover
MEASURE has no constraint dict — the L2d rubric (§42) is sufficient.
✗
On fail: Appends each violated constraint + evidence to validator_feedback. L2d does not fire. Executor re-runs seeing exactly which constraints it missed.
L2d — Quality Rubric (DMAICGraderMiddleware) MIDDLEWARE / after_agent
Fires inside the executor as an after_agent hook. Full grader role, temperature 0.1. Per-criterion verdicts, not one overall score. The Belt never sees this loop. Fires only if L2a + L2b + L2c all passed.
✗
Tier 1 criterion fails — gate fails: Appends per-criterion failure to validator_feedback. Increments gate_attempts.
⚠
Tier 2 criterion fails — gate passes with warning: Written to PhaseState.acknowledged_gaps. Belt sees it at gate_review_node. Does not increment gate_attempts.
✓
All Tier 1 criteria pass: gate_attempts resets to 0. Output proceeds to gate_review_node.
Retry Loop — shared iteration cap, accumulated feedback

All layers pass → validator_feedback reset to []. Proceeds to gate_review_node. Belt reviews validated output.
— or —
Any layer still fails → gate_attempts == 3 → conditional edge to escalation_subgraph. Belt receives: what was attempted, what failed, full constraint list, all three feedback entries. Belt is final arbiter — the agent does not block or guess.
Key invariants
Accumulated, not replaced. Each retry receives every prior failure, not just the most recent one. An executor that fixes L2c on attempt 2 still sees the L2c message on attempt 3 alongside the L2d message — so it cannot accidentally re-break what it already fixed.
Attempt number signals urgency. attempt=3 in the generation prompt tells the model this is the last chance — be more specific, not more verbose.
Cap is shared, not per-layer. A cap that resets per layer is not a cap. A system that fails L2a three times, then L2c three times, has run six attempts against the Belt's expectation of at most three.
Feedback resets on pass. validator_feedback = [] when all layers pass. The next phase starts clean.
Three-prompt separation in this loop: generate_decision() is the generation prompt. validate_constraints() (L2c) is a separate validation LLM call — it does not know how the decision was produced. The executor re-running on retry is the correction prompt — a fresh invocation with a different input (the feedback list), not a continuation of the prior call. These three roles are always separate .invoke() calls; they are never merged into one prompt.
